## المبادئ المعتمدة

1. إصلاح الـDesign Primitives والمكونات المشتركة قبل ترقيع الصفحات.
2. البيانات المعروضة حقيقية من Runtime/API؛ لا بطاقات شكلية أو قيم تجريبية.
3. لا تغيير لعقود التقييم الأكاديمية أو المحتوى canonical بسبب متطلبات العرض.
4. Pending Audio لا يمنع الطالب من إكمال بقية أسئلة الجلسة؛ الانتظار يكون عند نهاية الأسئلة إذا بقيت مراجعات معلقة.
5. Rerecord مهمة صريحة يفتحها الطالب، ولا تخطفه تلقائيًا من مساره.
6. Human Supervisor Review تبقى السلطة الأكاديمية للتسجيلات؛ لا Fake ASR ولا Audio Skip.
7. النجاح البرمجي وحده لا يكفي؛ الإغلاق يتطلب Regression Tests + Visual QA على أحجام فعلية.

## A — Student Question System

المشكلات:
- حاوية النص تستخدم حجمًا/ارتفاعًا كبيرًا حتى عندما يكون المحتوى جملة أو عبارة قصيرة.
- عنوان السؤال كبير على الهاتف.
- خيارات الصور تترك فراغات أكبر من الصورة.
- ترتيب الصور يحتاج عناصر أصغر والتفافًا أوضح على الهاتف.
- يجب الحفاظ على إصلاحات audio queue للضغط السريع والانتقال بين الأصوات.

العقد البصري:
- حرف/رمز قصير جدًا: عرض بارز وكبير.
- كلمة: عرض كبير ولكن أقل من الحرف.
- عبارة/جملة: حجم متوسط مرن مع طول النص والمساحة.
- الحاوية تتبع المحتوى ولا تفرض ارتفاعًا ضخمًا.
- الصور `object-fit: contain`، والبطاقة تتبع الصورة مع Touch Target آمن.
- ترتيب الصور يظل مقروءًا بدون بطاقات ضخمة.
- نفس المبادئ يجب أن تصل إلى الاختبار والأنشطة وContent Preview لمنع drift.

## B — Student Dashboard & Journey

الترتيب المطلوب:
1. هوية الطالب + المستوى الحالي + حالة الرحلة.
2. الإجراء الرئيسي الآن: أكمل الاختبار / تابع نشاطك / إعادة تسجيل / انتظار مراجعة.
3. خط الرحلة: قبلي → مستوى → أنشطة → تقوية عند الحاجة → بعدي.
4. تقدم المستوى: الأنشطة المنجزة + المهارات + التقدم الحقيقي.
5. الشارات والنجوم من بيانات حقيقية فقط.
6. النتائج والسجل كمعلومات ثانوية.

الهدف: Dashboard رحلة، وليس مجموعة بطاقات متساوية الأهمية.

## C — Admin Audio Review Workflow

المشكلة الحالية:
- قائمة التسجيلات ومساحة قرار المراجعة لا تملك hierarchy واضحًا.
- أزرار الاستماع/بدء المراجعة غير متوازنة على الهاتف.
- نموذج الاعتماد فيه فراغات كبيرة، قيم ملتصقة بعناوينها، وControls تبدو كنصوص.

التدفق المعتمد:
`التسجيل → استماع → قرار → أدلة/ملاحظات عند الحاجة → حفظ`

يجب أن تكون Approve وRequest Rerecord قرارات واضحة، ثم تظهر الحقول ذات الصلة فقط عند الحاجة.

## D — Admin Dashboard & Notifications

المشكلة:
- Dashboard يكرر بطاقة `تسجيل جديد يحتاج مراجعة` لكل Recording.

العقد:
- Dashboard يعرض Aggregates فقط مثل `3 تسجيلات بانتظار المراجعة`.
- التفاصيل الفردية داخل Review Queue / Notifications.
- لا تكرار لنفس الحدث بين Attention Area وNotifications وReview Queue.
- الضغط على الملخص يفتح الصفحة التشغيلية المناسبة.

## E — Remaining Admin UX

إعادة مراجعة إلزامية:
- زر/صفحة إضافة طالب.
- ملف الطالب وتبويباته على الهاتف.
- Content Preview وطريقة انتقال المشرف بين المحتوى كما يظهر للطالب.
- Toast System.

Toast contract:
- Success/Info تختفي تلقائيًا تقريبًا خلال 2.5–4 ثوانٍ.
- Error غير الحرج يبقى أطول قليلًا ويمكن إغلاقه.
- الأخطاء التي تحتاج قرارًا تظهر Inline قرب الإجراء، لا Toast فقط.
- النقر على Toast يغلقه، وأي Feedback جديد يستبدل القديم حسب السياق.

## قائمة Regression إلزامية قبل الإغلاق

- Admin login + الرجوع للرئيسية.
- Student login + الرجوع للرئيسية.
- Add student.
- Student profile mobile tabs.
- Image-choice sizing.
- Image-sequence ordering.
- Short/medium/long stimulus sizing.
- Mobile question title.
- Rapid audio click + switch audio without sticky error.
- Pending Audio journey.
- Rerecord explicit task.
- Student Dashboard real progress/results/badges.
- Audio Review list + Review decision form.
- Admin Dashboard aggregated attention states.
- Toast auto-dismiss/dismiss interaction.
- Content Preview fidelity.
