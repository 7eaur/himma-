## 0. الهدف وحدود المشروع

**الهدف النهائي:** منصة هِمّة V2 تستخدم **بنك البيانات الحالي 300 بندًا** بصورة صحيحة عبر 19 درسًا و12 دعمًا واختبارين من 30 بندًا. واجهة الطالب: **تمهيد → فيديو → تدريب 3–4 بتلميحات → اختبار مستقل 3–4** (L3-02: ثلاثة). دعم حسب الفجوة مع تحقق 2–3. تكون بيانات V2 الجديدة هي المرجع الرئيسي للتشغيل؛ البيانات القديمة ليست شرطًا وظيفيًا للانتقال، مع عدم حذف أي بيانات حقيقية قبل جردها وحفظها والحصول على إذن صريح. يعرض النظام نتائج دقيقة للمشرف مع احترام دور المراجعة البشرية للصوت.

**خارج النطاق ما لم يثبت الاحتياج:** بناء CMS كامل، إعادة هندسة كل الباكند أو كل الداشبورد، نقل الاستضافة دون ضرورة، محرك mastery/graph ضخم، اعتماد AI لتصحيح القراءة دون قياس وقرار مستقل، وتغيير قواعد التسكين الرقمية اعتباطًا.

**النطاق داخل الخطة:** المحتوى والتعاقدات، الواجهات، APIs، قاعدة البيانات عند الحاجة فقط، النسخ والتمهيد/الفيديوهات/التدريبات/الاختبارات، العرض الآمن، الكتابة الحرة والصوت في الخيارات، التكيف والتقوية، مراجعة الصوت البشرية، القبلي/البعدي، المشرف والتقارير، الوسائط، الأداء/RTL/الإتاحة، الأمان، اختبارات الاستيراد، والنشر الآمن.

## 0.1. متى نعتبر النظام مكتملًا قبل وصول الفيديوهات؟

- **جاهز تقنيًا بالوسائط التجريبية:** جميع الواجهات/APIs/المشغلات/التكيف/الدعم/القبلي والبعدي/التسجيل/الكتابة/لوحة المشرف والتقارير تعمل من أول الدخول إلى الإكمال على Staging، مع فيديو fixture صريح بكل الاختبارات، وملفات ميديا توضيحية غير معتمدة محجوبة عن الإنتاج.
- **جاهز لإضافة الأصول:** لكل فيديو/صوت/صورة `asset_id` ثابت وتوصيف ونواقص ودور وسائط وواجهة ربط/تبديل وإجراءات QA، من غير تغيير المنطق البرمجي.
- **ليس جاهزًا للنشر إلا بعد توفير الأصول:** تحميل 19 فيديو فعليًا، واستكمال الصور والأصوات ومراجعتها، وضمان عدم وجود سؤال يستلزم وسيطًا مفقودًا. اختبارات التشغيل بالـfixture لا تمنح اعتمادًا تربويًا نهائيًا.
- **قاعدة لا تُكسر:** غياب وسيط أساسي لا يُعالَج بتجاوز الفيديو أو السؤال أو توليد إجابة/درجة وهمية. يظهر Missing Media في أدوات الإشراف والاختبار فقط، وتمنع بوابة الإنتاج تفعيل الدرس غير المكتمل.

**مصفوفة التغطية الملزمة لجميع الوظائف والحالات:** `22_FULL_SYSTEM_COVERAGE_AND_ACCEPTANCE_MATRIX_AR.md`. كل متطلب فيها يُربط باختبار ومعيار إغلاق، وليس مجرد كلام وصفي.

## 0.2. السياسة الدقيقة: بيانات الاستخدام القديمة ≠ أصول المشروع المهمة

**المقصود بالبيانات القديمة غير المهمة للترحيل هو بيانات التشغيل المتولدة أثناء استخدام V1، وليس الصور أو الهوية أو التصميم أو المحتوى أو ملفات المشروع.**

| التصنيف | أمثلة محددة | قرار V2 |
|---|---|---|
| **بيانات تشغيل V1 غير مطلوبة وظيفيًا** | حسابات الطلاب الحالية، أكواد دخولهم، تقدمهم، محاولاتهم، درجاتهم ونتائجهم، تسجيلاتهم الصوتية الشخصية القديمة، سجلات الجلسات والاستخدام والبيانات التي أُنشئت أثناء التجربة، والحسابات التشغيلية القديمة التي سنستبدلها | **لا نُلزم V2 بترحيلها.** تبدأ منصة V2 بحسابات وتقدم ونتائج جديدة حسب الخطة. القديم يبقى معزولًا/محفوظًا بأمان وفق المتطلبات المعمول بها إلى اتخاذ قرار مستقل بشأنه. |
| **أصول المشروع المهمة والمرجعية** | شعار هِمّة والهوية والألوان والخطوط والأيقونات، الرسومات والشخصيات والأنميشن والصور التعليمية، الملفات الصوتية **التعليمية** المسجلة مسبقًا، تصميم الواجهات وأنماط التفاعل، الكود والمكونات الصحيحة، الإعدادات المعمارية النافعة، الأسئلة والمواد التعليمية المرجعية، ملفات البحث والتوثيق المطلوبة | **نفحصها ونستفيد من الصالح منها ونحسّنه أو نعيد إنتاجه إن كان أضعف من المستوى المطلوب.** لا تُحذف عند تنظيف قاعدة الطلاب أو بدء V2 من جديد. |
| **بنك V2 المعتمد للتطوير** | 19 درسًا، 12 دعمًا، 300 بندًا وقوائم الصور والصوت والفيديو الجديدة | **المصدر الأساسي للمحتوى الجديد.** لا نرجع إلى بنك V1 كبديل عنه. |

**التمييز الحاسم:** التسجيل الصوتي الذي أداه طالب قديم = بيانات مستخدم سابقة، **وليس** أصلًا تعليميًا ينبغي نقله. صوت قارئ تعليمي أو صوت حرف معتمد في المكتبة = أصل تعليمي **مرشح للاستخدام**، وتُراجع دقته قبل اعتماده في V2.

- **P01 فحص V1 من الجذور**: Frontend، Backend، DB، API، التكيف، التسجيل، المشرف، التصميم، الهوية، الصور، الوسائط، الأداء، الأمان، رحلة الطالب وكل التبعيات. لكل وظيفة أو أصل قرار `keep | refactor | replace | retire_after_review`.
- يُفضّل بدء V2 بقاعدة تشغيل نظيفة إن أثبت التدقيق ملاءمتها. لا نضيّع وقت التطوير في استيراد نتائج وتجارب الطلاب القدامى ما دام ذلك لا يخدم نسخة V2.
- **عدم الحاجة إلى الترحيل ليس إذنًا بالحذف.** بيانات الطلاب الشخصية والتسجيلات الموجودة فعلًا تُفحص التزامات حفظها وخصوصيتها، وتُعزل أو تُحفظ بصورة آمنة قبل أي تصرف، والحذف الدائم يحتاج موافقة منفصلة.
- ممنوع حذف الصور أو الأصول التعليمية أو الهوية أو تصميم الشاشات أو مكونات الكود النافعة بحجة «بيانات V1 غير مهمة». الاحتفاظ بما ثبت صلاحيته لا يتعارض مع إعادة بناء الجوانب الضعيفة جذريًا.
- لا نبقي وحدتين تؤديان العمل نفسه إلى الأبد: كل استبدال يمر باختبارات قبول، ثم يُزال المسار غير المطلوب دون مساس بأصول المشروع المرجعية.

## 0.3. تحديث V1 في مكانها — ميزة غير مذكورة لا تُلغى

**معيار المالك الأحدث (2026-10-18):** هذه النسخة هي **تحديث شامل لنفس منصة هِمّة**، وليس إعادة إنشاء منتج جديد ينسخ من V1 ما يختاره المطور. تبقى **كل وظائف وميزات V1** ضمن النطاق افتراضيًا — حتى لو لم تذكر في وثائق بنك محتوى V2.

- قبل أي إعادة هيكلة/استبدال، راجع **`25_V1_TO_V2_FEATURE_PARITY_REGISTER_AR.md`** الذي يسجل مزايا الطالب والمشرف والتقارير والتصدير والإشعارات والمكافآت والأمان والميديا والمراجعة والجلسات. **32 عائلة وظائف أولية مرصودة في المصدر؛ الجرد يجب أن يكتمل قبل اعتماد P01.**
- أبقِ القدرة والسلوك النافعين حتى لو تغيرت الواجهة أو API أو جدول DB؛ لا ينجح refactor إن عطّل ميزة قديمة صالحة لا يغطيها بنك الدروس.
- استبدال الوحدة يجوز كحل جذري **داخل المشروع ذاته** وبعد فحص جميع المستهلكين واعتماد البديل وتحقق regression؛ لا تضف نظامًا موازيًا قائمًا طويلًا أو فرع منتج منفصلًا.
- لا تنفذ حذف ميزة بسبب عدم ذكرها. الإلغاء الوحيد بإجراء `RETIRE_APPROVED` واضح من المالك، مع السبب والمخاطر والاختبارات.
- استثناء **البيانات الشخصية التاريخية** فقط: حسابات الطلاب القديمة/تقدمهم/تسجيلاتهم ومحاولاتهم **غير مطلوب ترحيلها**؛ وظائف إنشاء الحسابات/إدارة الطلاب والتسجيل الصوتي ومراجعة التقدم تظل مطلوبة بنسخة V2 الجديدة.
- **Gate P09 وP10:** تقرير parity لكل `Fxx` مع دليل، وليس مجرد مرور سيناريوهات L1/L2/L3؛ أي ميزة قديمة مفقودة دون استثناء موقع تمنع الإطلاق.

## 1. قاعدة تنفيذ لكل مرحلة

1. **Baseline:** تحديد HEAD الفعلي لكل فرع أو بيئة، ومقارنتها مع البنك والتوثيق. لا افتراض أن تخطيط V2 منشور أو أن كل تغييرات فرع V2 صالحة للدمج.
2. **Root cause أولًا:** إثبات المشكلة بالملف/الاختبار والسبب البنيوي؛ أي تغيير يجب أن يعالج العقد أو المصدر المسؤول، لا إضافة استثناءات سطحية في مكونات React.
3. **تغيير معزول:** فرع/Commits محددة للمرحلة، دون لمس `stage/02-content` أو إنتاج Railway إلا ضمن Gate النشر وبموافقة.
4. **لا تغيير أسماء الدوال بلا ضرورة موثقة**؛ نعيد استخدام خدمة/مكوّن أو نعيد تنظيمه بتقسيم واضح، بلا تكرار بين الواجهات وخلفية التصحيح.
5. **اختبارات ثم مراجعة:** فحص آلي + حالات سعيدة/فشل + فحص بصري للهاتف والديسكتوب للمرحلة التي تؤثر على الواجهة.
6. **تحديث سجلات المرجع:** توثيق قرار كل تغيير وربطه بـCommit/CI/بيئة المعاينة، وتحديث سجل المرحلة `21_EXECUTION_PROGRESS_AR.md`.
7. **بوابة إغلاق:** مكتمل فقط إذا اجتاز معايير القبول ولم توجد P0/P1 مفتوحة ضمن نطاق المرحلة؛ التوثيق لا يساوي اختبارًا ناجحًا.
8. **توقف للاعتماد:** لا تقدم للمرحلة التالية من دون اعتماد المستخدم الصريح. لا دمج أو نشر لمجرد نجاح الاختبارات.

**المخرجات:** media import/bind contract يعمل + سجلات النقص + تقرير يبيّن بالضبط ما ينبغي توفيره آخرًا.

**Gate:** النظام الفني يكتشف الميديا الناقصة ويمنع تشغيلها في الإنتاج، ويقبل استبدال الوسيط دون تعديل منطق الدرس. **Gate الوسائط الإنتاجية النهائي ينفذ في P10**.

**Gate:** 62 قراءة في البنك لها مسار واقعي للمراجعة والقرار، لا loss ولا fake grade ولا كشف صوتيات؛ الطفل يستطيع متابعة ما تسمح به السياسة.

### P09 — اكتمال المنصة وظيفيًا وتجربة المسارات كلها **قبل توفير الفيديوهات النهائية**

**الهدف:** تسليم منصة V2 تجريبية مكتملة الوظائف، يتبقى فيها إدخال ملفات الإنتاج ومراجعتها فقط، لا وحدات برمجية.

1. تشغيل جميع الـ300 بند من البنك في staging بفيديو fixture موضَّح، وأصول اختبار تمثل كل نمط وسائط، وفحص المستويات والدروس والدعم والقبلي والبعدي وكافة الشاشات.
2. تنفيذ مصفوفة `22_FULL_SYSTEM_COVERAGE_AND_ACCEPTANCE_MATRIX_AR.md` نقطة بنقطة، مع evidence لكل نقطة، ومحاكاة طالب يبدأ L1/L2/L3 حتى البعدي والمشرف والصوت والكتابة والتكيف والدعم والتقدم.
3. اختبار فيديو كامل: تشغيل وتحميل وإيقاف/استمرار وخطأ/تعافٍ وقطع اتصال/بطء وتبديل وضع الهاتف/ميديا مفقودة ومحاولة تخطي المحتوى ومشاهدة جزء من الفيديو.

5. اختبار الأمن والخصوصية/فصل الإجابات وAPI authorization والعزل، والاستيراد بإصدار جديد والجلسات القديمة إن لزم وعدم إعادة احتساب submit.
6. CI شامل Backend/Frontend/API/E2E وقياسات أداء حقيقية وشبكة بطيئة وخطة تصحيح P0/P1 من الجذور؛ لا ترقيع لتجاوز اختبار.
7. توقيع **بوابة الأداء الوظيفي** `functional_ready_with_test_media` منفصلة عن `media_complete`، وتوثيق أن قائمة النواقص الأخيرة **مواد إنتاج فقط**. إذا بقي تغيير كود مطلوب لا نعلن الجاهزية.

**المخرجات:** نسخة staging متكاملة وظيفيًا + لقطات/فيديو تجربة + تقرير اختبار شامل + قائمة أصول إنتاج نهائية على مستوى معرف.

**Gate:** كل السيناريوهات الفنية ناجحة، **وكل مزايا V1 المسجلة F01–F32 وملاحقها مثبتة وظيفيًا أو ملغاة بموافقة مستقلة**، ولا توجد P0/P1 وظيفية مفتوحة، لا أسئلة ناقصة/معطلة، كل فجوات الأصول معروفة ومكتملة الوصف. **لا يشترط توفر الفيديوهات النهائية لتوقيع بوابة الجاهزية الوظيفية، ولكن يمنع النشر والاعتماد التعليمي النهائي قبل توفيرها.**

### P10 — توفير الأصول النهائية وربطها ثم قبول الإنتاج والإطلاق

**لا تبدأ إلا بعد قبول P09 الوظيفي ومعاينة مختص للمحتوى، وقبلها تتوفر تجهيزات التخزين والإدارة والمشغّل والعقود كاملة.**

1. تسليم ملفات الفيديوهات النهائية الـ19، والصور/الأصوات الناقصة أو البديلة لأصول V1 الضعيفة؛ حفظ source/rights/QA/approved_version لكل أصل.
2. إضافة الملفات من media import/bind المجهز، وتحويل الحالات من `pending/missing` إلى `reviewed/approved` بعد فحص السمع/النطق/المعنى/مستوى الصوت والترجمات والجودة والمتانة على شبكة ضعيفة.
3. إجراء `Full Media-to-Question Integrity Check`: كل درس يشغل فيديوه المعتمد، وكل سؤال يعرض صوره وأصواته وخياراته ولا يسرب الإجابة، ونص القراءة ومرجعه الصحيح.
4. استبدال Fixtures، ثم إعادة جميع E2E والشاشات ومسارات الطالب والمشرف والتكيف والدعم والاختبارين على نسخة Release Candidate **بالوسائط الحقيقية**.
5. **قرار بيانات استخدام V1:** يجوز بدء V2 بقاعدة جديدة دون نقل حسابات الطلاب السابقة وتقدمهم ونتائجهم وتسجيلاتهم الشخصية ومحاولاتهم؛ هذا **لا يشمل الشعار والهوية والتصميم والصور والأصوات التعليمية والكود النافع** التي تجرد وتُراجع لإعادة الاستخدام. لا حذف لبيانات طلاب حقيقية دون جرد وحفظ وموافقة مستقلة. اختبار backup/restore/rollback وقائمة أسرار البيئة دون حفظها في GitHub.
6. تجربة انتقال Preview/Staging → canary إن أمكن، ومراقبة logs والمخاطر والأداء/التخزين، مع خطة عودة تشمل كود التطبيق وإصدار المحتوى والبيانات.
7. موافقة نشر منفصلة وواضحة بعد Gate P10، ثم إطلاق تدريجي وفحص smoke حقيقي ومراقبة أخطاء وسلوك الطالب.

**Gate:** `functional_ready` + `media_approved` + `academic_signoff` + `regression_passed` + `backup_restore_rollback_verified` + `owner_release_approval`. إن لم تجتمع، لا نشر.

## 5. اختبارات الحواجز الحرجة التي لا تُؤجل

| الخطر | اختبار القبول المطلوب |
|---|---|
| كشف الحل أو النص المنطوق | JSON student API لا يتضمن `private_answer` أو `reading_reference` أو خيارًا يحمل label كاشفًا |
| سؤال صورة/صوت يظهر فارغًا | لكل asset والاختيار حالة تحميل/تشغيل/خطأ مفهومة وإجابة قابلة للتحديد |

| فقد تقدم الطالب | خروج/عودة وتحديث الصفحة/تكرار إرسال API لا ينشئ تكرار نتيجة |
| درجات التدريب تختلط بالاختبار | سجل evidence يفصل النوعين والقرارات لا تستعمل تلميحات كتقييم |

| تكرار الدعم لا ينتهي | سقف محاولات + fallback واضح للمشرف/التعلم اللاحق |
| عبث بمحتوى منشور | `ContentRelease` immutable وchecksum وتدرج الإصدارات |
| كسر مستخدمي V1 | migration تجريبي/backup/restore وRegression للمتصفح والـAPI |
