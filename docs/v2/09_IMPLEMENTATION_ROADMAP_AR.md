**الحالة:** خطة تنفيذ معتمدة كاتجاه، لم تبدأ مراحل تعديل الكود بعد.

## 0. الهدف وحدود المشروع

**الهدف النهائي:** منصة هِمّة V2 تستخدم **بنك البيانات الحالي 300 بندًا** بصورة صحيحة عبر 19 درسًا و12 دعمًا واختبارين من 30 بندًا. واجهة الطالب: **تمهيد → فيديو → تدريب 3–4 بتلميحات → اختبار مستقل 3–4** (L3-02: ثلاثة). دعم حسب الفجوة مع تحقق 2–3. يحافظ النظام على بيانات V1، ويعرض نتائج دقيقة للمشرف مع احترام دور المراجعة البشرية للصوت.

**خارج النطاق ما لم يثبت الاحتياج:** بناء CMS كامل، إعادة هندسة كل الباكند أو كل الداشبورد، نقل الاستضافة دون ضرورة، محرك mastery/graph ضخم، اعتماد AI لتصحيح القراءة دون قياس وقرار مستقل، وتغيير قواعد التسكين الرقمية اعتباطًا.

**النطاق داخل الخطة:** المحتوى والتعاقدات، الواجهات، APIs، قاعدة البيانات عند الحاجة فقط، النسخ والتمهيد/الفيديوهات/التدريبات/الاختبارات، العرض الآمن، الكتابة الحرة والصوت في الخيارات، التكيف والتقوية، مراجعة الصوت البشرية، القبلي/البعدي، المشرف والتقارير، الوسائط، الأداء/RTL/الإتاحة، الأمان، اختبارات الاستيراد، والنشر الآمن.

## 1. قاعدة تنفيذ لكل مرحلة

1. **Baseline:** تحديد HEAD الفعلي لكل فرع أو بيئة، ومقارنتها مع البنك والتوثيق. لا افتراض أن تخطيط V2 منشور أو أن كل تغييرات فرع V2 صالحة للدمج.
2. **Root cause أولًا:** إثبات المشكلة بالملف/الاختبار والسبب البنيوي؛ أي تغيير يجب أن يعالج العقد أو المصدر المسؤول، لا إضافة استثناءات سطحية في مكونات React.
3. **تغيير معزول:** فرع/Commits محددة للمرحلة، دون لمس `stage/02-content` أو إنتاج Railway إلا ضمن Gate النشر وبموافقة.
4. **لا تغيير أسماء الدوال بلا ضرورة موثقة**؛ نعيد استخدام خدمة/مكوّن أو نعيد تنظيمه بتقسيم واضح، بلا تكرار بين الواجهات وخلفية التصحيح.
5. **اختبارات ثم مراجعة:** فحص آلي + حالات سعيدة/فشل + فحص بصري للهاتف والديسكتوب للمرحلة التي تؤثر على الواجهة.
6. **تحديث سجلات المرجع:** توثيق قرار كل تغيير وربطه بـCommit/CI/بيئة المعاينة، وتحديث سجل المرحلة `21_EXECUTION_PROGRESS_AR.md`.
7. **بوابة إغلاق:** مكتمل فقط إذا اجتاز معايير القبول ولم توجد P0/P1 مفتوحة ضمن نطاق المرحلة؛ التوثيق لا يساوي اختبارًا ناجحًا.
8. **توقف للاعتماد:** لا تقدم للمرحلة التالية من دون اعتماد المستخدم الصريح. لا دمج أو نشر لمجرد نجاح الاختبارات.

### قاعدة معمارية

```text
V2 versioned Content Bank (authoring/private)
    ↓ validate → normalize → approved content release
FastAPI authoritative lesson/attempt/evidence endpoints
    ↓ safe student DTO: no answer keys / no hidden grading rubrics
React student lesson shell + shared interaction renderer
    ↓ submit/idempotency/progress
Attempts/Evidence + Support decision + Supervisor review
```

**لا يُقدم بنك المؤلف الخام كاملًا إلى المتصفح** لأنه يحوي `private_answer` ومعايير تصحيح ومراجع للقراءة. المصدر العام يتكون في الخلفية مع whitelist حقول صريح واختبارات عدم تسريب.

## 3. المراحل التفصيلية وGates الإغلاق

### P00 — الجرد والتوحيد وتثبيت البنك — **المرحلة الجارية**

**المشكلة:** وثائق V2 السابقة تدعي أن التأليف 2/19 أو أن الخطوة التالية تأليف L1-03 بينما البنك موجود كاملًا.

**العمل:**
- إثبات محتويات البنك الحالي وعدد البنود وتفرد المعرفات وربط الأسئلة وتوثيق blobs.
- تعيين مصدر حقيقة واحد للقرارات، والعقود، والخطة، وبنك المحتوى.
- تصنيف الوثائق القديمة وحذف المتكرر المنسوخ منها إذا أُغلق المرجع، دون حذف بنك أو تدقيق أو مستند عميل فريد.
- توثيق الفجوات التقنية والتربوية والوسائط ووضع سجل مراحل.

**المخرجات:** `README.md`، `DECISIONS_AR.md`، `13_CONTENT_BANK_AND_UNIFIED_TEMPLATES_AR.md`، `20_VERIFIED_CONTENT_BASELINE_AND_GAPS_AR.md`، هذه الخطة، `21_EXECUTION_PROGRESS_AR.md`.

**Gate:** روابط جميع الملفات صحيحة؛ رقم **300** مطابق؛ لا تناقض في عدد الأسئلة أو المرحلة التالية؛ جميع محتويات البنك محفوظة؛ لا تغييرات على الإنتاج أو V1.

### P01 — ضبط خط الأساس الهندسي والأمان والترحيل قبل أي كود

**العمل:**
- قراءة HEAD الحقيقي لـ`stage/02-content` ومقارنته بفرع V2 وبيئة Railway/Actions؛ تمييز تغييرات V2 المرتبطة بالمشروع عن تغييرات تراكمية قديمة غير مختبرة.
- جرد migrations، نماذج `ContentItem/ContentStep/ContentOption/ContentRelease`، المحاولات والجلسات والتقدم وأكواد الطلاب، عقود API والصوت والصلاحيات.
- بناء **مصفوفة Gap → الملف المسؤول → حل جذري → الاختبار**؛ كشف تعارض `write_text` وخيار الصوت وحفظ حالة الفيديو.
- تعريف حدود توافق V1/V2 (compatibility) ومسار بيانات المحتوى القديم والجلسات النشطة.
- تحديد خطة backup وrestore وميزة إتاحة V2 خلف feature flag، وموافقة منفصلة على أي تغيير DB.
- حفظ تقرير baseline CI حقيقي وتجهيز بيانات اختبار اصطناعية فقط.

**المخرجات:** تقرير هندسي مع فروع/SHAs وAPI contract/schema proposal وخطة بيانات وترحيل واختبار رجوع.

**Gate:** كل فجوة P0 لها تصميم ومالك واختبار؛ baseline CI مؤكد، إمكانية restore معروفة؛ لا Runtime/DB production modifications.

### P02 — عقد بنك المحتوى ومُحوّل استيراد مضبوط بالإصدارات

**العمل:**
- تعريف Schema مضبوط يغطي `lesson/support/question/media/assessment`، role (practice/check/pre/post)، `private_answer`، rubrics، error focus، origin_v1، وحالات assets.
- أداة validator تمنع missing refs / duplicate ids / inconsistent options / media issues / 3–4 questions rules / تسريب hint في check.
- مُحوّل واحد deterministic من بنوك JSON الأربعة إلى صيغة نشر المحتوى المعتمدة على FastAPI/SQLAlchemy؛ لا نسخ شرطيات لكل درس.
- **Draft→Review→Approved→Publish**؛ checksum لكل إصدار وحفظ snapshots immutable وعدم تبديل بنود منشورة قيد محاولة.
- فصل safe student DTO عن authoring DTO بخادم مسؤول عن إخفاء الإجابات ومراجع التصحيح.
- تشغيل dry-run وidempotent import/rollback على قاعدة تجريبية.

**المخرجات:** schema/validator/transformer/import pipeline موحد، migration ضيقة متوافقة مع V1 فقط عند الحاجة، اختبارات آلية.

**Gate:** تحويل 300 بند دون فقد/تكرار، فصل الإجابات في اختبار API، dry-run/re-run لا يكرر السجلات، V1 tests سليمة، rollback مجرب.

### P03 — محرك الدرس الموحد وحفظ رحلة الطالب

**العمل:**
- مشغل درس واحد بواجهات أربع فقط: `intro → video → guided_practice → independent_check`.
- State transition مسجل بالخادم (lesson/session/step) مع `resume` بعد قطع الإنترنت/تحديث الصفحة وعدم إعادة احتساب جواب.
- الفيديو من مكتبة الوسائط مع تحميل تدريجي ونص داعم/إتاحة، واستكمال مشاهدة فعلي دون التباس «عرض الفيديو = إتقان».
- زر أساسي واضح، شريط تقدم، وعودة آمنة إلى لوحة الطالب؛ تحكم في الخطوات من عقد backend لا JS فقط.
- قالب دعم يستخدم نفس مشغل الدرس مع تعديل بسيط في عدد البنود وبؤرة المهارة.

**المخرجات:** lesson shell + APIs + persistent progress + اختبارات تدفق واحدة على الأقل لـL1-01.

**Gate:** مسار الدرس كامل دون تداخل تمرين/اختبار، Resume يعمل بعد refresh وانقطاع اتصال، RTL هاتف وديسكتوب، لا تظهر إجابة اختبار.

### P05 — تسجيل الأدلة، التكيف، الدعم، والترقية

**العمل:**
- فصل إجابات guided practice (تعليم، hint/retry) عن independent check (قياس) على مستوى schema + API + policy.
- الاحتفاظ بأدلة `skill_group/evidence_type/error_focus/source/attempt`، وربط `SUP-01..12` وfocus لبيانات البنك دون إدخال شجرة قواعد غير ضرورية.
- انتقال جيد → الدرس التالي؛ دليل غير كافٍ → تحقق قصير؛ فجوة ثابتة → دعم مركّز، مع إنهاء حلقة الدعم وعدم الرجوع غير المنتهي.
- الحفاظ على **عدم الخفض الآلي**، ومعالجة فجوة المستوى السابق داخل المسار قدر الإمكان.
- اختبار قواعد التسكين والترقية الحالية، وتبرير أي اختلاف رقمي بعد مراجعة محتوى البنك وموافقة المستخدم.
- تدقيق صحة قرارات المشرف وتسجيلها في Audit Log.

**المخرجات:** adaptation integration على الأدلة الجديدة + دعم 12/focus + اختبارات سيناريوهات الحدود والتعارض.

**Gate:** خطأ واحد لا يرسل للدعم، لا loop لا نهائي، hint ليس إتقانًا، مستوى الطالب لا يتراجع آليًا، الحالات الصوتية المعلقة لا تتحول إلى نجاح.

### P08 — الصوت وتحليل القراءة المساعد (بدون تعطيل الإصدار)

**العمل:**
- تأكيد دورة `captured→uploaded→review→graded/rerecord` كما في V1؛ منع الاستخدام الأكاديمي لتسجيل pending.
- أسئلة التدريب التي تسجل قراءة: واجهة توضح حالة التسجيل، والسماح باستمرار التعلم وفق القواعد، دون تلميح صوتي غير مستند إلى حكم حقيقي.

**المخرجات:** مسار صوت آمن ومختبر، وتقرير قرار AI منفصل (تشغيل مساعد أو مؤجل).

**Gate:** لا احتساب تسجيل غير مُراجع، لا فقد تاريخ التسجيل، لا تسريب بيانات شخصية، وFallback المشرف يعمل دائمًا.

- مراجعة RTL والهاتف والتابلت والديسكتوب، قارئ الشاشة والتنقل بلوحة المفاتيح، الشبكة الضعيفة وحالات media failure.
- تدقيق تربوي نهائي من مختص/المالك لجميع النصوص الحساسة والمعايير، ومعايرة أولية للقبلي/البعدي دون استخدام بيانات حقيقية غير مأذونة.
- مقارنة مؤشرات السرعة والتقارير مع V1 من baseline مثبت، ومعالجة أي تدهور غير مبرر.

**المخرجات:** تقرير اختبارات فعلي مرتبط بSHA ولقطات شاشة، قائمة P0/P1 مغلقة، رأي تربوي موثق.

**Gate:** نجاح CI وE2E وNo regression، لا P0/P1 مفتوحة، اكتمال مراجعة المحتوى والوسائط وقواعد التقييم، نجاح تجربة كاملة.

### P10 — الترحيل والإطلاق الآمن

**شروط البداية:** P00..P09 مغلقة ومعتمدة، نسخة V2 تجريبية وموافقة نشر صريحة.

**العمل:**
- نسخة احتياطية وتحقق restore لبيانات الطلاب والتسجيلات، وقائمة بيئة Railway الحية وأسرارها دون نسخها إلى GitHub.
- rehearsal لترحيل المحتوى وschema/canonical releases، مع قياس زمن الترحيل وأثر الجلسات النشطة؛ استرجاع كامل إذا فشلت خطوة.
- نشر Preview/Staging ومعاينة طرفي الطالب والمشرف، ثم canary / feature flag حسب الإمكانيات الحقيقية.
- خطة rollback تشمل **الكود + إصدار المحتوى + توافق البيانات**؛ لا نفترض إمكانية downgrade للبيانات بسلامة دون اختبار.
- الموافقة الأخيرة قبل دمج الفرع والنشر؛ متابعة السجلات والأخطاء والنتائج بعد الإطلاق.

**المخرجات:** سجل نشر بالـSHA/CI/backup/rollback وتجربة smoke وقرار قبول.

**Gate:** تشغيل V2 مطابق للبنك المعتمد، عدم فقد بيانات V1، اختبارات إنتاج smoke ناجحة، rollback مُجرّب، وموافقة المستخدم الصريحة.

## 5. اختبارات الحواجز الحرجة التي لا تُؤجل

| الخطر | اختبار القبول المطلوب |
|---|---|
| كشف الحل أو النص المنطوق | JSON student API لا يتضمن `private_answer` أو `reading_reference` أو خيارًا يحمل label كاشفًا |
| سؤال صورة/صوت يظهر فارغًا | لكل asset والاختيار حالة تحميل/تشغيل/خطأ مفهومة وإجابة قابلة للتحديد |
| `write_text` بلا معيار | حفظ UTF-8/RTL، rubric آمن، قبول اختلافات صحيحة متفق عليها، مراجعة عند الحاجة |
| فقد تقدم الطالب | خروج/عودة وتحديث الصفحة/تكرار إرسال API لا ينشئ تكرار نتيجة |
| درجات التدريب تختلط بالاختبار | سجل evidence يفصل النوعين والقرارات لا تستعمل تلميحات كتقييم |
| تسجيل لم يُراجع يحتسب نجاحًا | `pending` محايد ويظل للمشرف قرار نهائي |
| تكرار الدعم لا ينتهي | سقف محاولات + fallback واضح للمشرف/التعلم اللاحق |
| عبث بمحتوى منشور | `ContentRelease` immutable وchecksum وتدرج الإصدارات |
| كسر مستخدمي V1 | migration تجريبي/backup/restore وRegression للمتصفح والـAPI |

## 6. ملف الحالة ومبدأ الإغلاق

توثق كل مرحلة في `21_EXECUTION_PROGRESS_AR.md`:

## 7. تعريف النجاح النهائي

عند الإطلاق يكون لدى الطالب **مسار عمل فعلي** من الدخول والقبلي إلى دروس V2 والتدريب والاختبار والدعم والتقييم البعدي، وعند المشرف مراجعات صوت/كتابة ونتائج موثوقة؛ تعمل كل أسئلة الـ300 مع وسائطها في قوالب قابلة لإعادة الاستخدام، مع التزام الخصوصية والتحسين الجذري وعدم تعريض V1 لتغيير غير قابل للعكس.
