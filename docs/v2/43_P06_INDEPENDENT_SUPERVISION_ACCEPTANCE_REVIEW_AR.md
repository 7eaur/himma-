## 2. مشكلات مؤكدة يجب إغلاقها ضمن نطاق P06

### SUP-P06-01 — P0: المراجع لا يستطيع الاطلاع على الدليل قبل التقييم
- **الدليل:** `services/api/v2_assessment_runtime.py` الأسطر 369–390: طابور V2 يعرض metadata فقط، ولا يُرجع نص كتابة الطالب أو تشغيل التسجيل أو النص المرجعي؛ ويسمح بتحديد `is_correct` مع ملاحظة. `apps/web/src/app/admin/(dashboard)/v2-assessments/page.tsx` تعرض أزرار مستوفٍ/غير مستوفٍ بلا عرض الدليل.
- **سبب جذري إضافي:** `services/api/review.py` الأسطر 25–72 (طابور V1) يرشح `AudioSubmission.status='uploaded'` ويلتحق بـ`AttemptResponse`، في حين ينشئ P06 تسجيل V2 بالحالة `pending_review` و`assessment_response_id` (انظر `v2_assessment_runtime.py` 340–351). لذا صفحة مراجعة V1 ليست عارضًا صالحًا لأدلة V2.
- **الإصلاح المطلوب:** إنشاء عرض تفصيلي V2 آمن للمشرف يربط `AssessmentQuestionResponse` بالطالب والسؤال والمرجع المسموح للمراجع والإجابة المكتوبة، أو مسار تشغيل خاص للصوت عبر تحقق RBAC/الملكية. راجع الدليل أولًا ثم اسمح بالقرار، واعرض حالة التحميل والخطأ. لا تمرر `private_answer` إلى الطالب ولا تستخدم S3 عامًا. لا تنشئ نظام مراجعة موازيًا غير ضروري؛ استفد من التخزين والمكونات الآمنة الموجودة.
- **اختبارات القبول:** Test API لمراجعة كتابة وسماع قراءة فعلية، Student 403، Cross-student/cross-role forbidden، اختبار رفض اعتماد بلا دليل، سريان القرار إلى `waiting_review → placement_pending_review`، Playwright UX للمشرف.

### SUP-P06-02 — P0: تعدد المحاولات الرسمية عند إعادة الاختبار
- **الدليل:** `services/api/v2_assessment_runtime.py` الأسطر 189–193 و403–410 تضع `official_for_reporting=True` مباشرة في إكمال البعدي واعتماد تسكين القبلي. لا تصفر علم المحاولات السابقة للطالب/نوع التقييم. `services/api/assessment_retake.py` 86–90 تتضمن الدالة المشتركة `mark_official_completed_attempt` التي تصفر القديمة. `v2_assessment_runtime.py` 436–447 تجمع متوسطات كل الجلسات الموسومة official، مما يسمح بتكرار احتساب نفس الطالب.
- **الإصلاح المطلوب:** استخدم خدمة رسمية واحدة atomic لضمان محاولة رسمية واحدة للطالب ونوع التقييم، بما يشمل V1/V2 وإعادة الاختبار؛ حافظ على تاريخ المحاولات و`supersedes_session_id` وسجل Audit، واعالج التزامن وقيد DB الملائم دون حذف سجلات.
- **اختبارات القبول:** مسار قبلي/بعدي مع retake مأذون مرتين، تحقق official واحدة فقط لكل نوع، حساب متوسط واحد، عدم تسريب جلسات غير رسمية للتقارير، واختبار concurrency تحت PostgreSQL.

### SUP-P06-03 — P1: تجربة التسكين اليدوي غير مكتملة
- **الدليل:** لوحة المشرف `apps/web/src/app/admin/(dashboard)/v2-assessments/page.tsx` تعتمد إدخال رقم session يدويًا عبر نموذج، بينما الملخص يوفر **عدد** الجلسات المنتظرة فقط، ولا يعرض قائمة الجلسات المؤهلة وبيانات الطالب ونتائج المهارات لتكوين قرار موثق.
- **الإصلاح المطلوب:** قائمة eligible placement scoped وتفاصيل نتائج V2 لكل جلسة، مع اختيار مستوى وسبب من نموذج صريح داخل AdminShell (بدلاً من الاعتماد على raw ID و`window.prompt`). حافظ على قواعد السياسة المرشحة دون تخمين threshold.
- **اختبارات القبول:** جلسة تنتظر التسكين تظهر مع الطالب والنتائج؛ تختفي بعد القرار؛ Reject غير الجاهزة أو غير المصرح لها؛ mobile/keyboard/RTL.

### SUP-P06-04 — P1: ثبات معرف إصدار المحتوى للمحاولات المتجددة
- **الدليل:** `services/api/v2_assessment_runtime.py` الأسطر 86–105 و100–106 تستخرج قائمة الأسئلة وسؤال الجلسة من `get_release()` العام دون استخدام `session.content_release_id`، و`services/api/v2_content/repository.py` تُبقي `get_release()` cached من بنك GitHub الحالي. هذا خطر عند نشر بنك N+1 بينما هناك جلسة مثبتة على N.
- **المطلوب:** اختبارات PostgreSQL مستقلة لحالة Start على N ثم تعديل candidate في N+1 مع استئناف وتصحيح وربط السؤال الصحيح على N. أصلح source lookup إذا ثبت فقدان immutable pin، ولا تفتح إصدارًا معتمدًا بلا تحكيم.

### SUP-P06-05 — P1: حدود تشغيل الإدارة والانتظار
- **الدليل:** الطابور في `v2_assessment_runtime.py` 371 وملخص التقرير في 438 يستخدمان `.all()` دون pagination؛ الملخصات تستعلم الجلسات/النتائج منفصلة، وواجهات V2 ما زالت دون اكتمال تفويض cohort/claim. بعضها أوسع نطاقًا ضمن P08/P09 حسب الخطة.
- **المطلوب الآن ضمن P06:** لا تسمح لمشرف بمراجعة أدلة خارج صلاحياته؛ أضف اختبارات السعة والـquery budget للتقارير/الطابور أو سجل فصل المسؤوليات وأسباب تأجيل تحسين غير مانع مع ضوابط trial. لا تختصر مراجعة الدليل الفعلية إلى P08.

## 3. عوائق تحقق لا تُسجل كأعطال مؤكدة

- **تسجيل دخول المشرف بعد reset:** وثيقة 42 تسجل نجاح إعادة تعيين bcrypt، لكن تجربة كاملة بعد العملية (تسجيل الدخول/redirect/session) لم تُؤكد من المالك. لا تطلب ولا تسجل كلمة المرور؛ يستحسن تدوير كلمة المرور السابقة إلى قيمة قوية وفريدة بأداة إدارة أسرار آمنة.
- **Visual/E2E:** اختبار المسار الكامل لنفس الطالب (قبلي 30، صوت وكتابة، مراجعة، تسكين، درس وتقوية، بعدي، تقارير) على جهاز حقيقي، وسلامة مشغل الميديا و360/390/430/tablet/desktop و200% وaxe، غير مثبت هنا. P09 يوسّع التغطية، لكن الحد الأدنى لشاشة P06 والمراجعة مطلوب قبل قبول P06.
- **الاعتماد التربوي:** تكافؤ صعوبة 30+30 وحدود التسكين ومراجعة 12 صوتًا و56 أصل V1 والفيديوهات النهائية ما تزال معلقة؛ trial فقط دون أطفال أو بيانات فعلية.
- **تصدير PDF/XLSX وV1 parity:** الوظائف القديمة موجودة بالمصدر، لكن تكامل صادرات V2 والتحقق من عدم التراجع الحقيقي مؤجلان. «لم يُحذف ملف» ليس مرادفًا «الميزة مجرّبة».
- **Readiness:** `/ready` ما يزال مرتبطًا بحزمة V1؛ لا تغيّر Healthcheck لتمرير أخضر زائف، وخطط Readiness حقيقية لـV2.
- **Auto deploy:** `checkSuites=false` خطر قبول تحديث فاشل، وwatchPatterns للفيديو غير شاملة. تحسين التشغيل شرط خطة حواجز آمنة، دون تعطيل معاينة المالك أو زيادة الخدمات والموارد.
