## 2) المشروع المقصود وقرارات المنتج التي لا يجوز تجاوزها

**هِمّة V2 تحديث لنفس المنصة التعليمية القائمة** (FastAPI + SQLAlchemy/Alembic + Next.js، بيانات PostgreSQL، Redis، تخزين S3)، وليست منصة أخرى تستلهم القديمة. نحفظ جميع الوظائف الموجودة أصلًا ما لم يُعتمد قرار محدد ومدعوم بالاختبارات باستبدالها/تعديلها: التسجيل والدخول، إدارة الطلاب، لوحة الطالب والمشرف، الاختبارات، الدروس، التقوية، المكافآت، الإشعارات، التسجيلات والمراجعات، التقارير وتصدير PDF/XLSX، والصفحات العامة. نحافظ على هوية هِمّة والشعارات والخطوط والشخصيات والصور/الأصوات التعليمية والمكونات المفيدة، مع إصلاح جذري لا ترقيع.

قرار عدم حمل **بيانات الطلاب التاريخية** من V1 لا يسمح بحذف قدرات المنصة أو الأصول التعليمية. لا حذف سجلات/تسجيلات أشخاص فعلية دون تقييم خصوصية ونسخة احتياطية وموافقة مستقلة. لا Docker في هِمّة. لا تغيير أسماء الدوال بلا سبب وحاجة. حل جذري منظم واختبارات منع تراجع لكل مشكلة معروفة.

المنهج المعتمد للطالب: قبلي شامل يغطي المهارات، ثم تسكين مسؤول لا يتجاوز فجوة مؤثرة، ثم 3 مستويات L1/L2/L3، فـ**التمهيد → فيديو الأهداف والأمثلة → تدريب 3–4 مع تلميح → اختبار 3–4 مستقل بلا تلميح**؛ تقوية داخل المستوى أو مدمجة في المسار عند الحاجة، دون حلقات تكرار أو خفض تلقائي اعتباطي؛ قراءة جهرية وكتابة تنتظر أدلة تقييم بشرية حين يلزم. البعدي بعد استكمال الشروط. السكون والشدة في مواضعهما التعليمية بلا تشكيل زائد، والطلاقة تعني النطق الصحيح لا مجرد السرعة. لا استخدام إجابات خاصة أو مراجع نطق مخفية في DTO الطالب؛ بنك التأليف لا يُرسل للواجهة خامًا.

## 7) مشكلة تسجيل الدخول وكلمة مرور المشرف — محلولة تقنيًا وتحتاج smoke test

المستخدم فتح `/admin/login` على iPhone؛ ظهرت أولًا رسالة `مصدر الطلب غير مسموح` وHTTP 403. تحليل log `himma-web` في Railway أكد `POST /api/auth/login = 403` قبل التحقق من كلمة المرور. السبب الجذري في `apps/web/src/app/api/proxySecurity.ts`: مقارنة `Origin` بعنوان `req.nextUrl.origin` الداخلي خلف HTTPS reverse proxy الخاص بـRailway. جرى إصلاحه ليستخدم **`RAILWAY_PUBLIC_DOMAIN` الموثوق** فقط عندما يكون موجودًا، مع رفض `cross-site` وOrigin مختلف. تعديل الكود `4ba46dcaf57f02ae35dafe11e595fe66125ff7a1`، واختبارات `proxySecurity.test.ts` في `c228c3a7a857d7aa27ccbf5de2feb8cbc853d7c5`. نشر Web على ذلك الـSHA `SUCCESS`، واختبارات CI/M04/M09 ناجحة.

بعد إصلاح CSRF صارت محاولات الدخول الفعلية ترجع 401 بدل 403: نتيجة عدم تطابق كلمة مرور المشرف المخزنة bcrypt في PostgreSQL مع متغير Railway. **تغيير `ADMIN_PASSWORD` في Variables لا يغيّر user.password_hash الموجود تلقائيًا.** استُخدم مسار `services/api/db/seed.py` الأصلي idempotent مع راية إعادة ضبط مقصودة، وأُعيد نشر `himma-`؛ ظهر نص log مؤكد **`Admin password reset applied by explicit seed flag.`**، ثم `Seeding completed successfully.` وhealth 200، وdeployment `961cfe35-bea9-4f4e-b4ed-a309354bf4fb` وصل `SUCCESS`.

**أمان ما بعد العملية:** أعيد `preDeployCommand` إلى `cd services/api && alembic upgrade head && python -m db.seed`، وضُبط `RESET_ADMIN_PASSWORD_ON_SEED=false` دون redeploy إضافي. تأكد من هذه الإعدادات الحية عند أي متابعة. اسم المستخدم الافتراضي `admin`؛ **لا تُسجّل كلمة المرور نفسها**. لأنها أُرسلت سابقًا داخل المحادثة وكانت قصيرة، اطلب من المالك تدويرها إلى سر قوي وفريد ثم غيّر تجزئة قاعدة البيانات من مسار إداري آمن. **لم تُنفّذ تجربة ناجحة لتسجيل دخول حساب المشرف بالفعل بعد إعادة التعيين**؛ هذا هو اختبار المتابعة التالي، دون حاجة لجمع كلمة المرور في الدردشة. لا تُشغّل reset تلقائيًا دائمًا.
