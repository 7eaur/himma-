## Root cause and change
`InteractionPlayer` used an answer idempotency key per question but allowed a learner to change the answer after an ambiguous POST failure (e.g. lost 503 acknowledgment). A retry with the old key and changed body causes server 409, while using a new key could accidentally answer a *different* question if the first submission advanced server state. A lost response after recording upload could also cause redundant reupload.

The fix retains the **exact pending answer body + submit_key** after a potentially committed POST; locks option/ordered tray/textarea/recording controls until the same request is acknowledged; retries without reuploading an already uploaded recording; and clears the pending request only on confirmed success or definite input rejection (400/422). A new recording receives a new upload key. The server's idempotency enforcement remains unchanged. Tests assert both ambiguous retry and definite rejection paths.
